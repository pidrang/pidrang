# Contributing to Pidrang

Thank you for considering contributing to Pidrang.

## Questions and ideas

Ask questions and share ideas in [GitHub Discussions](https://github.com/pidrang/pidrang/discussions). Open an issue for a reproducible bug or a concrete feature request, using the templates. Report security problems privately, as described in [`SECURITY.md`](./SECURITY.md).

## Local setup

Requirements: Node.js 22.22.3 or later, and pnpm (the exact version is pinned in `packageManager`; `corepack enable` picks it up).

```bash
git clone https://github.com/pidrang/pidrang.git
cd pidrang
pnpm install
pnpm exec nx serve demo-material
```

The demo apps talk to the hosted `pidrang` Supabase project by default. To run against a local Supabase instance instead:

```bash
# in a clone of pidrang/supabase
supabase start

# in this repo
pnpm exec nx serve demo-material --configuration=local
```

## Before opening a pull request

```bash
pnpm exec nx run-many -t lint test build
```

CI runs this command, then `node tools/release-gate/run.mjs --mode build`: it packs the seven packages, installs the tarballs in two empty Angular apps (one on `@pidrang/material` with pages generated by the installed CLI, one on `@pidrang/tailwind`) and builds them in strict mode. It needs network access. To limit the first command to one project, use `-p`, for example `pnpm exec nx run-many -t lint test -p core`.

When a change touches the demos, the generated pages, the Supabase provider or packaging, also run the full release gate locally (see [Releasing](./docs/releasing.md#the-release-gate)): it runs both apps and both demos in a browser against a local Supabase stack loaded with the test fixtures. A pull request from a branch of this repository runs it in CI too, but a pull request from a fork cannot, so run it before opening one.

## Architecture rule

`@pidrang/core` depends on `@angular/core` only: no component library, no `@angular/common`, `@angular/forms`, `@angular/platform-browser` or `@angular/router`. Subpaths of `@angular/core`, such as `@angular/core/rxjs-interop`, are allowed; `rxjs` and every other package are not. Lint enforces this. A change that seems to need one of those belongs in a UI package. See [`docs/architecture.md`](./docs/architecture.md).

## Code style

- Follow the official Angular conventions: standalone APIs, signals over `Observable` state, `inject()` over constructor injection.
- Do not write code comments, including doc blocks. Lint rejects them. Lint suppressions such as `eslint-disable` and `@ts-expect-error` are comments too, so they are not allowed either. Make the code self-explanatory through naming and small functions, and put the reason for a non-obvious choice in the commit message, the pull request description or [`docs/design-notes.md`](./docs/design-notes.md).
- Add or update tests next to the code they cover.

## Branching

- `main` is always releasable.
- Work happens on short-lived branches: `feat/*` for features and packages, `fix/*` for bug fixes, `docs/*` for documentation, `chore/*` for tooling.
- Open a pull request against `main`. CI must pass before merging.

## Commit messages

Commits follow [Conventional Commits](https://www.conventionalcommits.org/). The release tooling reads them to decide the next version and to build the changelog, so the type matters:

- `feat(core): add getList provider contract`
- `fix(supabase): handle null response in update`
- `docs: update README roadmap`

Use `feat` for new behavior, `fix` for bug fixes, and add `!` after the scope (for example `feat(core)!: rename injectResource`) or a `BREAKING CHANGE:` footer for breaking changes. Scopes are package names without the `@pidrang/` prefix: `core`, `supabase`, `material`, `tailwind`, `cli`, `cli-supabase`.
