# @pidrang/cli

Provider-agnostic engine behind `pidrang init`: the interactive wizard, the `Resource` codegen, and the contract every schema provider (Supabase today, REST/Strapi/GraphQL later) implements against. Never imports a concrete provider package (e.g. `@pidrang/cli-supabase`) — that wiring happens one level up, in `apps/pidrang-cli`.

## Exports

- `SchemaProvider` — `listTables()`, `introspectTable(table)` — what a concrete provider implements once connected. `introspectTable` returns a `TableIntrospection`: the `fields` to generate, the `excludedColumns` left out with a reason, and the `unavailableActions` the wizard shows as disabled with their reason
- `IntrospectedColumn`, `describeTable(table, columns, unavailableActions?)` — the shared rule a provider uses to build a `TableIntrospection`: a column whose `type` is `{ unsupported }` is left out, and makes create unavailable when it needs a value on insert and has no visible default; edit is unavailable when no kept field is writable
- `SchemaProviderDefinition<TConnection>` — `id`, `label`, `planHelp`, `promptConnection()`, `connectionFromPlan(connection, env)`, `createSchemaProvider(connection)` — how the wizard discovers and connects to a provider without knowing its connection shape. `connectionFromPlan` builds the connection from a plan file's `connection` object and reads secrets from `env` only; `planHelp` describes that object for `pidrang --help`
- `CrudAction` — `'list' | 'create' | 'show' | 'edit' | 'delete'`, and `CRUD_ACTIONS`, the five in that order
- `GenerationPlan`, `TablePlan` — the wizard's output: per selected table, its fields, chosen actions, and fields to hide from list/edit views
- `runInitWizard(providers, options?)` — drives the interactive flow, returns a `GenerationPlan`. `options.takenRoutes` lists the route segments the app already uses; a table with one of those names is refused
- `InitPlan`, `TableSelection`, `parseInitPlan(value)` — the plan file of `pidrang init --plan`: `provider`, `connection`, and per table `table`, `actions` and optional `hiddenFields`. `parseInitPlan` refuses unknown properties, empty or repeated actions, unknown actions and repeated tables, listing every problem at once
- `runScriptedInit(providers, plan, env, options?)` — the same `GenerationPlan` as the wizard for the same choices, without prompts: it runs every check the wizard runs, plus that each table is one the provider lists and each hidden field is a kept field. `options.reportLeftOutColumns(message)` is called once per table that leaves columns out, with the line the wizard shows in its actions question
- `generateResourcesFile(plan: GenerationPlan)` — pure string generator, turns a plan into a ready-to-use `resources.ts` (no disk I/O)
- `generatePagesBundle()`, `RESOURCE_ROUTES_SNIPPET`, `SIGN_IN_PATH_SNIPPET` (the optional provider that turns the pages' sign-in prompt into a link; it imports `provideSignInPath` from the generated `src/app/pidrang/provide-sign-in-path.ts`, which refuses an empty, malformed or outside-the-app path when called) — the generic List/Create/Show/Edit pages from `apps/demo-material` plus their helpers from `libs/demo-shared` (written under `src/app/pidrang/` with imports rewritten to relative paths), generated by `pnpm run sync:pages` (see `docs/design-notes.md`), plus the routes to wire them up. Scoped to `@pidrang/material` for now — these pages are resource-agnostic and shared across every table, so they're generated once, not per table. No disk I/O here either; writing them into the target app is `apps/pidrang-cli`'s job.

## Running unit tests

Run `nx test cli` to execute the unit tests via [Vitest](https://vitest.dev/).

## Building

Run `nx build cli` to build the library.
